# 任务阶段与两端进度

网页/SSE 和 Telegram 状态卡共用 `module/task_progress.py` 的只读投影，避免各自从百分比猜测是否完成。投影不调用模型、不修改任务或资源。

## 展示规则

| 实际阶段 | 下载 | 上传 | 状态 |
| --- | --- | --- | --- |
| 下载中 | 实际已下载字节占比 | 没有上传记录则为0，不模拟 | 下载中 |
| 下载完整、正在分析 | 100% | 0%，待上传 | AI分析中 |
| 分析结束、尚未上传 | 100% | 0%，待上传 | 等待上传 |
| 上传中 | 已下载字节占比 | 实际上传字节占比 | 上传中 |
| 上传字节传完、整项流程尚未确认 | 100% | 100% | 确认上传，仍属进行中 |
| 确认完成 | 100% | 100% | 已完成 |

完成态优先于残留上传进度；若本地完成标记之后还有实际的部分上传，则仍显示上传中。暂停、下载失败和上传失败保持独立，不因字节达到100%而变成成功。其他账号的上传记录不能改变当前任务的阶段或错误说明。

接口百分比始终为数值字符串，不再返回 `Finishing...`。前端兼容旧响应，但百分比不再决定完成状态。下载结束后的旧下载速度、暂停/分析/确认/完成阶段的速度均不作为实时传输速度展示；Telegram不借用其他任务的全局速度。

Telegram分别显示下载、上传进度；成功/失败/跳过数属于「任务结果」，在包含分析和上传的流程结束后结算，不再命名为「总体进度」。尚未取得大小的文件不会编造字节总量，汇总注明已知文件数量。最近文件只有真正完成才显示成功标记，正在分析或确认上传的文件显示当前阶段。

## 批次隔离

- 有运行时文件成员表时，只接受该 TaskNode 实际包含的消息，不以显示任务编号关联整个历史。
- 兼容旧节点时，同时校验账号、任务编号和创建时间，排除节点创建之前的历史记录。
- 新任务编号在已有历史及运行节点的最大编号之后分配，分配过程加锁；空闲重启不会复用仍保留在历史中的编号。
- 不迁移或删除旧历史，不改写既有分析结果。Telegram已经结束的历史消息不会自动重新编辑；新卡片和仍在刷新的卡片使用新格式。

## Telegram送达确认

部署前日志还确认存在Telegram拒绝频繁刷新（429）的情况。旧代码在请求前缓存卡片文本、在文件处理结束后直接移除节点，会丢失最后一次状态更新。

- 仅在编辑成功或服务器确认内容未改变后缓存已送达文本。
- 同一卡片只允许一个编辑请求在途，后续刷新重新读取最新任务状态，不排队重放旧进度。
- Bot API结构化 `retry_after` 和Pyrogram `FloodWait` 共用冷却窗口，冷却期间不继续提交卡片编辑；普通网络错误稍后重试。等待通过下一次后台刷新实现，不阻塞下载。
- 已完成节点保留到最终卡片确认送达；已删除/无权限的卡片明确停止重试，不误记为送达。
- 最终状态不受普通刷新频率限制，但仍遵守服务器限流等待；发送旧快照期间完成的任务，必须再发送一次真正的最终快照。

等待时长按 [Telegram ResponseParameters](https://core.telegram.org/bots/api#responseparameters) 的定义读取，不从错误文案猜测秒数。

## 回归

`tests/module/test_task_progress.py` 从网页投影和真实Telegram格式化入口注入相同的合成记录；不连接Telegram、不下载媒体、不调用模型。覆盖分析期误报、上传确认、终态数值、速度、旧批次混入、跨账号错误隔离、暂停/失败、编号分配及取消任务的归属判断。新增用例已在修复前复现失败，修复后通过。

`tests/webui/task_progress.scenarios.cjs` 使用离线SSE驱动真实前端，覆盖桌面/手机、待上传、分析、确认上传、完成及旧 `Finishing...` 响应；随 `resource_library.browser.cjs` 运行。可用 `TASK_PROGRESS_ONLY=1` 单独执行这一组。

`tests/module/test_task_status_delivery.py` 使用模拟Telegram响应与虚拟时钟，复现失败缓存、限流未等待、终态节点提前清理和并发旧快照覆盖；覆盖两种Telegram客户端、普通临时错误、无权限、已送达但响应丢失。全部不发送真实消息。

更广回归中发现原有 `/help` 测试要求图片，而 `HEAD` 中的帮助函数已改为文本；对未修改的HEAD函数独立复跑同样失败。本轮不改帮助行为、不删除该用例；验收记录将其作为既有失败列出。
